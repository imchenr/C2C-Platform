# 基于 FastAPI 与 Vue 的校园二手商品交易平台设计与实现

## 毕业论文详细写作框架

适用对象：当前工作区内已经完成的“校园集市”项目。系统采用 Python 3.12、FastAPI、SQLAlchemy、SQLite、Vue 3、Vite、Vue Router、Pinia、Axios、Element Plus 与 ECharts，实现 C 端和管理后台，现有 14 个主要数据实体、49 个 API 接口。

使用说明：本框架不是论文正文，而是“逐节写作施工图”。每一节均说明写作目的、核心内容、建议证据、图表安排和容易出现的问题。学校模板、字数、参考文献格式与章节数量如有强制要求，应以学校规范为准。

## 一、对参考论文的研究结论

### 1.1 参考论文的整体组织方式

参考文档共 53 页，采用较典型的软件工程类毕业论文结构：封面、诚信声明、中文摘要、关键词、目录、绪论、相关技术、系统分析与设计、系统实现、系统测试、结论、参考文献、致谢与论文评定表。正文按照“提出问题—介绍技术—分析需求—完成设计—展示实现—开展测试—总结展望”的顺序展开，符合信息系统设计与实现类论文的基本叙事逻辑。

参考论文将系统论证材料分成四类：一是研究背景和文献现状；二是用例图、架构图、时序图和 E-R 图等设计证据；三是数据库表、类方法和系统界面等实现证据；四是功能、响应时间、压力与账号安全等测试证据。这个组织方式值得保留。

### 1.2 参考论文值得借鉴的做法

- 论文结构覆盖软件工程全过程，没有只写页面截图，也没有只讲技术概念。
- 技术章节能够说明技术在系统中的具体用途，而不是只给出百科式定义。
- 需求与设计章节使用用例图、架构图、时序图、E-R 图和数据表形成证据链。
- 实现章节按业务模块展开，每个模块同时描述处理流程和页面结果。
- 测试章节区分功能测试、性能测试和安全性测试，具备结果验证意识。
- 结论部分区分研究成果和未来展望，能够回扣绪论中的问题与目标。

### 1.3 参考论文需要避免的问题

- 章节编号存在不统一现象，部分一级标题缺少章号或小节号，目录层级与正文层级不完全一致。
- 个别图号重复，例如同一章出现重复的“图 4-4”，图题格式也不完全统一。
- 有些技术性能数字或高并发结论缺少测试环境、样本量和原始结果支撑，容易形成“先有结论、后补证据”。
- 部分内容出现对象名称前后不一致、疑似笔误以及数据库字段解释含混的问题。
- 相关技术内容篇幅较长，但部分内容与后续核心实现联系较弱。
- 参考文献的真实性、时效性和引用位置必须逐条核验，不能只在文末堆放文献。
- 界面截图较多但清晰度不一，部分页面缺少对用户目标、关键操作和实现机制的解释。

### 1.4 新论文的改写原则

新论文保留参考论文的完整软件工程链路，但统一采用“章—节—小节”三级编号；每一个功能必须能够追溯到需求、设计、接口、数据实体、实现页面和测试用例；技术章节只介绍项目真实使用的技术；性能和安全结论必须来自实际测试；对尚未实现的真实支付、强实名认证、WebSocket 实时消息等能力，明确写成系统边界或未来工作，不得包装成已实现成果。

## 二、论文定位与题目建议

### 2.1 推荐题目

| 优先级 | 论文题目 | 适用说明 |

| 推荐 | 基于 FastAPI 与 Vue 的校园二手商品交易平台设计与实现 | 技术准确，能直接对应当前代码与系统成果 |
| 备选 | 基于 Python 与 Vue 的校园二手商品交易平台设计与实现 | 表述更宽泛，适合学校要求题目不出现具体框架时使用 |

建议使用第一项。标题中的“FastAPI”负责体现后端技术特征，“Vue”负责体现前端技术特征，“校园二手商品交易平台”限定研究对象，“设计与实现”明确论文类型。

### 2.2 研究对象

研究对象不是一般电商平台，而是面向高校学生的单件闲置商品交易平台。系统围绕“同校发现、商品发布、校内沟通、创建订单、面交履约、信用评价、内容审核和风险处理”构建业务闭环，并分别提供学生用户使用的 C 端和运营人员使用的管理后台。

### 2.3 核心问题

论文应围绕以下问题形成主线：传统校园闲置交易依赖社交群和线下口头沟通，存在信息分散、检索困难、身份可信度不足、交易过程缺少留痕、违规内容难以治理、运营数据不可统计等问题；如何使用前后端分离技术构建统一平台，并通过权限控制、审核机制、订单状态管理、消息与通知、举报处理和数据可视化提升校园交易效率与可管理性。

### 2.4 研究目标

第一，完成覆盖商品发布、浏览、收藏、沟通、订单、评价与举报的 C 端功能；第二，完成覆盖用户、商品、订单、举报、运营内容和系统配置的管理后台；第三，建立清晰的数据库模型、REST API 与权限边界；第四，通过功能、接口、权限、兼容性和性能测试验证系统可用性；第五，总结当前原型在真实认证、并发锁定、支付和售后等方面的边界。

### 2.5 可提炼的特色与创新点

创新点应克制表达，建议写成“设计特色”而不是夸大为算法创新。

- 面向校园二手交易场景设计同校信息、校区取货地点、实名认证状态、信用分和面交安全提示。
- 将 C 端交易流程与管理后台审核、举报、公告、轮播、分类、配置和审计日志连接起来，形成双端协同。
- 使用订单状态机描述待处理、已付款、待面交、已完成、取消、退款和争议等业务状态，使交易过程可追踪。
- 以商品为上下文组织会话，减少聊天内容与交易对象脱节的问题。
- 使用 Vue 3 响应式前端与 FastAPI REST 服务实现前后端分离，并通过 SQLAlchemy 完成领域实体映射。
- 使用 ECharts 展示近七日交易趋势和商品分类分布，为后台运营提供数据支持。

### 2.6 论文必须声明的实现边界

- 当前付款操作是校园面交业务状态模拟，没有接入第三方资金支付与真实账务系统。
- 当前校园认证属于演示级状态，不应声称已完成权威学籍系统核验。
- 当前消息使用 REST 接口读写，不应声称已经通过 WebSocket 实现真正实时推送。
- SQLite 适合课程设计和单机演示，生产环境应迁移到 PostgreSQL 或 MySQL 并补充并发控制。
- 测试章节只能填写实际测得的数据，未测数据必须保留为待完成项。

## 第 1 章 绪论

### 1.1 研究背景

写作目的：说明为什么需要建设校园二手商品交易平台，使研究问题从宏观环境逐步落到具体校园场景。

### 3.3 系统角色分析

#### 3.3.1 游客角色

同时具有买家和卖家身份。买家可搜索、收藏、沟通、创建订单、推进交易、评价和举报；卖家可发布、编辑、下架商品，接收会话和订单，并查看交易状态。

具有数据概览、用户状态管理、商品审核、订单查询、举报处理、运营内容管理、系统配置和审计日志权限。

### 3.4 系统业务流程分析

#### 3.4.1 用户注册与登录流程

注册输入用户名、校园邮箱、密码、昵称、学校和学号；后端校验唯一性并哈希密码；登录支持用户名、邮箱或手机号；账号被暂停或封禁时拒绝登录；登录后根据角色进入 C 端或后台。

#### 3.4.2 商品发布与审核流程

用户上传图片并填写商品字段；后端根据配置将普通用户商品置为待审核；管理员审核通过后发布，驳回时写入原因并通知卖家；商品修改后重新进入审核；卖家可主动下架。

#### 3.4.3 商品浏览与沟通流程

用户按分类、关键词、价格、成色和排序检索；查看详情后可收藏或建立围绕该商品的会话；同一买家、卖家和商品组合复用一个会话。

#### 3.4.4 下单与面交流程

买家确认见面地点并创建订单；订单依次经历待处理、已付款、待面交和已完成，也可能取消、退款或产生争议；完成订单后商品置为已售，并允许双方评价。

应特别说明当前为业务状态模拟，真实上线需增加卖家接单、商品唯一锁定和取货码核销。

#### 3.4.5 举报与处理流程

用户针对商品、用户或订单提交原因与说明；管理员受理并标记处理中；完成核查后解决或驳回；处理结果以通知形式反馈举报人，并记录管理员审计日志。

前端支持多图片上传、表单字段、创建和编辑；后端检查分类、序列化图片数组并根据 `audit_required` 设置待审核或发布状态；普通用户修改后重新审核；管理员审核时更新状态、审核意见、通知和审计日志。

联系卖家时创建或复用商品会话；会话列表按最后消息时间排序并计算未读数；读取消息后将对方消息置为已读；发送消息时更新会话最后消息和时间。

### 5.8 订单创建与状态流转实现

本节核心是状态机，不要只展示订单页面。需解释每个动作允许的起始状态和操作者权限。

#### 5.11.1 用户状态管理实现

#### 5.11.2 商品审核管理实现

#### 5.11.3 订单查询管理实现

#### 5.11.6 系统配置与审计日志实现

### 5.12 文件上传与安全机制实现

后端检查扩展名、生成时间戳和随机文件名、保存至上传目录并返回 URL；密码采用 PBKDF2；令牌使用 HMAC；后端在资源修改、订单、会话和后台接口中进行所有权或角色判断。

## 第 7 章 总结与展望

### 7.1 研究工作总结

按照“问题—方法—设计—实现—测试—价值”总结，不再逐页复述。明确完成 C 端和后台、14 个主要实体、49 个 API、订单状态、内容审核、举报处理和运营图表等成果。性能结论必须引用第 6 章实测数据。

### 7.2 系统不足

建议诚实写出：校园认证为演示级；同一商品缺少跨买家的数据库级锁定和卖家接单；取货码尚未强制核销；没有真实支付与退款清算；消息不是 WebSocket 实时推送；SQLite 不适合生产高并发；信用分缺少动态模型；上传安全、登录限流、隐私合规和自动化测试仍需加强。

### 7.3 未来展望

按优先级写，而不是随意罗列：第一阶段补实名认证、商品锁定、卖家接单、取货码核销和售后工单；第二阶段迁移 PostgreSQL、对象存储、Redis、异步任务和 WebSocket；第三阶段增加求购广场、教材 ISBN/课程筛选、毕业季批量发布、地图交接点、议价和降价提醒；第四阶段在合规前提下探索推荐、风险识别和运营分析。

## 十、参考文献规划

### 10.1 文献数量与构成

建议准备 25—35 篇可核验文献，其中近五年文献占主要比例，英文文献不少于学校规定数量。参考文献可分为校园二手交易与循环经济、C2C 信任和信用、内容审核与交易安全、前后端分离架构、Vue/FastAPI/ORM、软件测试与可用性六组。

### 10.2 检索关键词

中文关键词：校园二手交易平台、大学生闲置交易、C2C 信任机制、二手电商信用评价、校园信息系统、FastAPI Web 系统、Vue 前后端分离、二手交易推荐、平台内容治理、软件系统测试。

英文关键词：campus second-hand trading platform、student recommerce、C2C trust mechanism、online marketplace reputation、second-hand e-commerce、FastAPI web application、Vue front-end architecture、marketplace content moderation、software usability testing。

### 10.3 来源优先级

优先使用中国知网、万方、Web of Science、IEEE Xplore、ACM Digital Library、ScienceDirect 等可检索论文；技术机制可引用 FastAPI、Vue、SQLAlchemy、OWASP 等官方文档。商业博客和问答网站只能用于开发参考，不宜作为主要学术文献。

### 10.4 引用规则

国内外研究现状的每个研究结论必须有引用；技术章节引用官方机制或权威论文；测试指标和行业数据注明来源；正文出现的每条参考文献都应在文末列出，文末每条文献也应在正文出现。不得直接沿用参考论文中的文献而不核验真实性。

## 十一、写作与开发补充任务

### 11.1 论文定稿前建议补充的开发工作

- 为同一商品增加跨买家的进行中订单唯一锁定或卖家接单机制。
- 将取货码改为实际核销条件，取消订单后隐藏或失效。
- 增加校园邮箱或管理员认证流程，避免填写学号即认证。
- 增加订单售后工单、证据和管理员裁决流程。
- 为系统设置中的自动取消、评价期限和敏感词开关补充真实后端规则。
- 增加 API 自动化测试、权限测试和数据初始化脚本。
- 为上传文件补充大小、MIME、图片解码和 EXIF 清理。
- 将生产密钥改为环境变量强制配置，增加登录限流。

这些工作并非全部必须在论文前完成，但 P0 交易一致性和自动化测试会显著提升论文质量。

### 11.2 论文材料采集顺序

第一步冻结论文版本和数据库；第二步生成架构、用例、状态和 E-R 图；第三步统一截取 C 端与后台页面；第四步导出数据库字段和 API 清单；第五步编写并执行测试用例；第六步采集性能原始数据；第七步整理缺陷与修复记录；第八步展开正文并逐节插入引用。

## 十二、最终自检清单

### 12.1 内容一致性

- 题目、摘要、关键词、目录、结论中的系统名称一致。
- 技术章节出现的技术都能在代码或部署环境中找到。
- 需求、设计、实现和测试之间能够按功能逐项追踪。
- 商品、订单、举报和用户状态名称在全文保持一致。
- C 端与管理后台的角色权限描述不互相矛盾。

### 12.2 证据真实性

- 性能数据保留测试脚本、时间、环境和原始结果。
- 页面截图来自最终版本，无遮挡、无演示工具边框和隐私信息。
- 文献在正式数据库中可检索，作者、题目、期刊、年份和页码准确。
- 未实现功能明确写为不足或展望，不使用“已实现”措辞。
- 测试结论包含失败、修复和遗留项，而不是笼统“全部正常”。

### 12.3 图表规范

- 图题置于图下，表题置于表上，编号按章连续。
- 所有图表在正文中先引用，图表内容与叙述一致。
- 流程图箭头方向统一，状态图包含开始、迁移和结束条件。
- E-R 图基数关系正确，表结构字段与 `models.py` 一致。
- 截图文字在打印尺寸下仍可辨认。

### 12.4 语言与格式

- 避免“非常强大”“极大提高”“完美解决”等无证据表述。
- 第一次出现英文缩写时给出中文和英文全称。
- 代码标识使用等宽格式或学校规定格式，不大段粘贴源代码。
- 章末小结只总结本章，不提前写下一章结果。
- 参考文献采用学校指定的 GB/T 7714 或其他统一格式。
